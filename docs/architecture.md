
# Архитектура распределённой системы мониторинга Linux-узлов вычислительного кластера

## 1. Назначение

Система предназначена для демонстрации распределённого мониторинга Linux-узлов вычислительного кластера. Она обеспечивает сбор технических метрик на стороне агента, доставку данных на центральный сервер, долговременное хранение снимков в PostgreSQL и визуализацию текущего состояния через веб-интерфейс.

Текущий этап проекта подтверждает работоспособность базового контура наблюдаемости:

```text
agent -> HTTP API -> server -> PostgreSQL -> web dashboard
```

## 2. Состав компонентов

### 2.1 Agent

Компонент `agent` запускается в Linux-среде и отвечает за:

- сбор показателей CPU из `/proc/stat`;
- сбор показателей памяти из `/proc/meminfo`;
- сбор сетевых счетчиков из `/proc/net/dev`;
- сбор информации по смонтированным файловым системам через `/proc/mounts` и `statfs`;
- формирование единого снимка `Metrics`;
- отправку снимка на сервер через HTTP `POST /api/v1/metrics`.

Агент работает циклически. Значение `COLLECTION_INTERVAL` используется как окно измерения для CPU и сетевой активности и фактически задает базовую периодичность отправки данных.

### 2.2 API module

Компонент `api` содержит общие Go-типы, которые используются агентом и сервером. Это снижает риск расхождения контракта данных между отправителем и получателем.

Основные типы:

- `Metrics`;
- `UsageWithCores`;
- `MemoryUsage`;
- `DiskUsage`;
- `NetworkUsage`;
- `Device`.

### 2.3 Server

Компонент `server` выполняет функции центрального узла приема и выдачи данных:

- принимает JSON-снимки метрик;
- валидирует обязательные поля `host_id` и `timestamp`;
- регистрирует или обновляет устройство в таблице `devices`;
- сохраняет снимок в таблице `metric_snapshots`;
- предоставляет API для веб-интерфейса и внешних клиентов;
- отдает статические файлы веб-панели из `server/web`.

HTTP-сервер слушает порт `8080`.

### 2.4 PostgreSQL

PostgreSQL используется как основное хранилище текущего этапа. Схема содержит две ключевые таблицы:

- `devices` — реестр известных узлов;
- `metric_snapshots` — история снимков метрик.

Снимок сохраняется в двух формах:

- агрегированные поля для быстрых выборок и последующей аналитики;
- JSONB-поля `cpu`, `memory`, `disk`, `network`, `raw` для сохранения полного исходного контракта.

### 2.5 Веб-панель

Веб-интерфейс расположен в `server/web` и отдается тем же сервером. Панель выполняет:

- загрузку списка устройств;
- выбор активного узла;
- отображение статуса online/offline;
- отображение последних значений CPU, памяти, RX и TX;
- построение графиков истории CPU, памяти и сетевого трафика;
- автообновление данных каждые 2 секунды.

Статус online вычисляется сервером на основании времени `last_seen_at`. Узел считается online, если последний снимок был получен не позднее чем 30 секунд назад.

### 2.6 Terminal dashboard

Каталог `dashboard` содержит экспериментальный терминальный интерфейс на Bubble Tea. Он использует те же API-эндпоинты, что и веб-панель. На текущем этапе основной демонстрационный сценарий проекта основан на `server/web` и Docker Compose.

## 3. Поток данных

1. Агент получает конфигурацию из переменных окружения.
2. Агент определяет `host_id`.
3. Агент параллельно запускает сбор CPU, памяти, дисков, сети и времени снимка.
4. Сформированный объект `Metrics` сериализуется в JSON.
5. Агент отправляет JSON на `SERVER_URL`.
6. Сервер декодирует тело запроса и выполняет минимальную валидацию.
7. Сервер выполняет upsert записи в `devices`.
8. Сервер сохраняет снимок в `metric_snapshots`.
9. Веб-интерфейс получает список узлов и историю по выбранному `host_id`.

## 4. Демонстрационный стенд Docker Compose

`docker-compose.yml` поднимает следующие сервисы:

- `postgres` — PostgreSQL 16 с инициализацией схемы из `server/migrations`;
- `server` — сервер приложения и веб-интерфейс на порту `8080`;
- `agent-node-1` — агент с `HOST_ID=node-1`;
- `agent-node-2` — агент с `HOST_ID=node-2`;
- `agent-node-3` — агент с `HOST_ID=node-3`.

В демонстрационном режиме агенты собирают метрики своей среды выполнения. Для мониторинга физических или виртуальных Linux-узлов агент должен запускаться непосредственно на соответствующем узле либо получать доступ к системным namespace и `/proc` целевой системы.

## 5. Границы ответственности

Агент:

- отвечает за локальный сбор данных;
- не хранит историю;
- не выполняет ретраи;
- не принимает входящие соединения.

Сервер:

- является единой точкой приема данных;
- отвечает за запись в PostgreSQL;
- предоставляет read API;
- обслуживает веб-панель.

PostgreSQL:

- хранит реестр узлов;
- хранит историю снимков;
- обеспечивает основу для дальнейшей аналитики и отчетности.

Веб-панель:

- является клиентом read API;
- не выполняет запись метрик;
- не содержит собственной бизнес-логики расчета статуса узлов.

## 6. Ключевые проектные решения

- Использование HTTP JSON упрощает демонстрацию, отладку и интеграцию.
- Общий модуль `api` фиксирует контракт между агентом и сервером на уровне типов.
- Сохранение полного `raw` JSON обеспечивает обратную совместимость при расширении схемы метрик.
- Разделение `devices` и `metric_snapshots` позволяет хранить историю по стабильному `host_id`.
- Docker Compose используется как воспроизводимый стенд для конференционной демонстрации.

## 7. Ограничения текущей архитектуры

- Нет аутентификации агентов и пользователей.
- Нет TLS-терминации на уровне приложения.
- Нет очереди доставки и повторных отправок при недоступности сервера.
- Нет политики хранения для ограничения объема исторических данных.
- Нет алертинга и правил пороговых уведомлений.
- Нет нормализованной многопользовательской модели доступа.

Эти ограничения не блокируют демонстрацию базового контура мониторинга, но должны рассматриваться как обязательные направления для промышленной эксплуатации.
