# Распределённая система мониторинга Linux-узлов вычислительного кластера

Проект представляет собой прототип распределённой системы мониторинга Linux-узлов вычислительного кластера. Система предназначена для сбора, передачи, хранения и визуализации базовых метрик узлов кластера. На текущем этапе реализован полный демонстрационный контур: агент собирает системные показатели, сервер принимает метрики по HTTP API, сохраняет данные в PostgreSQL и предоставляет веб-интерфейс для просмотра состояния узлов.

## Текущий статус

Реализованы:

- сбор метрик CPU, памяти, дисков и сети на стороне агента;
- формирование единого JSON-снимка состояния узла;
- передача снимков на сервер по HTTP;
- регистрация узлов по `host_id`;
- хранение истории метрик в PostgreSQL;
- API для получения списка узлов, последнего снимка и истории по узлу;
- веб-панель мониторинга с автообновлением, графиками и таблицей последних значений;
- Docker Compose-стенд с PostgreSQL, сервером и тремя агентами.

Текущая реализация ориентирована на демонстрацию архитектуры, контракта данных и базового сценария наблюдаемости. Механизмы аутентификации, TLS, алертинг, политика хранения данных и отказоустойчивая доставка метрик относятся к следующим этапам развития.

## Архитектура проекта

Основные компоненты:

- `agent` — агент мониторинга, запускаемый на Linux-узле или в демонстрационном контейнере.
- `server` — HTTP-сервер, принимающий метрики, работающий с PostgreSQL и отдающий веб-интерфейс.
- `api` — общий Go-модуль с типами контракта данных.
- `server/web` — браузерная панель мониторинга.
- `dashboard` — экспериментальный терминальный интерфейс для просмотра данных через API.
- `docs` — проектная документация.

Базовый поток данных:

```text
Linux-узел / контейнер
        |
        | agent: collection window
        v
metrics JSON snapshot
        |
        | HTTP POST /api/v1/metrics
        v
server
        |
        | PostgreSQL
        v
devices + metric_snapshots
        |
        | HTTP GET API
        v
web dashboard
```

## Быстрый запуск

1. Подготовить файл окружения:

```bash
cp .env.example .env
```

2. Запустить демонстрационный стенд:

```bash
docker compose up --build
```

3. Открыть веб-интерфейс:

```text
http://localhost:8080
```

4. Проверить состояние API:

```bash
curl http://localhost:8080/health
```

Ожидаемый ответ:

```text
ok
```

## Конфигурация

Сервер использует переменную:

- `DATABASE_URL` — строка подключения к PostgreSQL.

Агент использует переменные:

- `SERVER_URL` — полный адрес эндпоинта приема метрик, например `http://server:8080/api/v1/metrics`;
- `COLLECTION_INTERVAL` — окно измерения и базовый интервал сбора, по умолчанию `2s`;
- `REQUEST_TIMEOUT` — таймаут HTTP-запроса, по умолчанию `3s`;
- `HOST_ID` — явный идентификатор узла;
- `HOST_ID_FILE` — путь к резервному файлу идентификатора, если `HOST_ID` не задан.

Если `HOST_ID` не указан, агент пытается использовать `/etc/machine-id`, затем резервный файл, после чего при необходимости создает новый UUID.

## Основные HTTP-эндпоинты

- `GET /health` — проверка доступности сервера.
- `POST /api/v1/metrics` — прием одного снимка метрик от агента.
- `GET /api/v1/devices` — список зарегистрированных узлов.
- `GET /api/v1/devices/latest?host_id=<id>` — последний снимок по узлу.
- `GET /api/v1/devices/metrics?host_id=<id>&limit=<n>` — история метрик по узлу.
- `GET /debug/api` — диагностический эндпоинт последнего снимка; не является публичным контрактом.

Подробное описание API находится в `docs/api.md`.

## Важные ограничения текущего этапа

- Агент собирает метрики той Linux-среды, в которой он запущен. В Docker Compose-стенде это демонстрационные контейнеры с заданными `HOST_ID`.
- Доставка метрик выполняется синхронным HTTP-запросом без очереди и механизма повторной отправки.
- API не содержит аутентификации и авторизации.
- PostgreSQL-миграции в Docker Compose выполняются механизмом стандартной инициализации образа PostgreSQL при создании нового volume.
- Веб-интерфейс предназначен для оперативного просмотра состояния, а не для полнофункциональной аналитики.
